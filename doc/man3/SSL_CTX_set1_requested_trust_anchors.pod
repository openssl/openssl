=pod

=head1 NAME

SSL_CTX_set1_requested_trust_anchors, SSL_set1_requested_trust_anchors,
SSL_CTX_add1_requested_trust_anchors, SSL_add1_requested_trust_anchors,
SSL_get0_peer_available_trust_anchors
- set the trust anchors a TLS client requests

=head1 SYNOPSIS

 #include <openssl/ssl.h>

 int SSL_CTX_set1_requested_trust_anchors(SSL_CTX *ctx,
                                          const uint8_t *ids, size_t ids_len);
 int SSL_set1_requested_trust_anchors(SSL *ssl,
                                      const uint8_t *ids, size_t ids_len);
 int SSL_CTX_add1_requested_trust_anchors(SSL_CTX *ctx,
                                          const uint8_t *ids, size_t ids_len);
 int SSL_add1_requested_trust_anchors(SSL *ssl,
                                      const uint8_t *ids, size_t ids_len);
 void SSL_get0_peer_available_trust_anchors(const SSL *ssl,
                                            const uint8_t **out_ids,
                                            size_t *out_ids_len);

=head1 DESCRIPTION

These functions set the list of trust anchors a client requests from the server
in the B<trust_anchors> extension, so the server can select a certificate
issued by one of them (see
L<https://datatracker.ietf.org/doc/draft-ietf-tls-trust-anchor-ids/>).

I<ids> is the list in wire format: a series of nonempty, 8-bit
length-prefixed trust anchor IDs, each an identifier in binary form. I<ids_len>
is its length in bytes. The bytes are copied. Passing an empty list (I<ids_len>
zero) is permitted: the extension is still sent, with no identifiers, which
signals support for the retry mechanism without naming any trust anchor.

SSL_CTX_set1_requested_trust_anchors() configures the default for connections
created from I<ctx>. SSL_set1_requested_trust_anchors() configures a single
connection and overrides the context's setting for that connection.

If neither is called, the default list is advertised. It holds the identifiers
of the Merkle Tree Certificate CAs the client is configured to verify against
(see L<X509_STORE_trust_mtc_ca(3)>), followed by any identifiers added with
SSL_CTX_add1_requested_trust_anchors() and then
SSL_add1_requested_trust_anchors(). Calling SSL_CTX_set1_requested_trust_anchors()
or SSL_set1_requested_trust_anchors() replaces the whole default list,
including the Merkle Tree Certificate CA identifiers, with the supplied list.

SSL_CTX_add1_requested_trust_anchors() adds identifiers to the default list of
connections created from I<ctx>, and SSL_add1_requested_trust_anchors() adds
identifiers for a single connection. They are for trust anchors whose
identifiers are configured separately from the trust anchors themselves, such
as conventional CAs. Each call appends to the identifiers added by earlier
calls. Identifiers are not deduplicated. Once either function has been called,
the extension is sent even if the list is empty, so passing an empty list
signals support for the retry mechanism.

These functions only control what is advertised to the peer; they do not affect
certificate verification, which proceeds as usual against the configured trust
anchors.

SSL_get0_peer_available_trust_anchors() reports the trust anchors the peer said
it has a certification path for. It sets I<*out_ids> and I<*out_ids_len> to a
list in the same wire format, belonging to I<ssl> and valid until the handshake
completes. Only servers send available trust anchor IDs, so this outputs a list
only when I<ssl> is a client; otherwise, and when the peer sent no list,
I<*out_ids_len> is set to zero. A client that was sent a certificate it does not
trust can choose an identifier from this list and try again on a new
connection, requesting only that one.

=head1 RETURN VALUES

SSL_CTX_set1_requested_trust_anchors(), SSL_set1_requested_trust_anchors(),
SSL_CTX_add1_requested_trust_anchors() and SSL_add1_requested_trust_anchors()
return 1 on success and 0 on error, including when I<ids> is not a well-formed
list.

SSL_get0_peer_available_trust_anchors() does not return a value.

=head1 NOTES

Most callers do not need to set an explicit list. The default list, with the
identifiers of any other trust anchors added to it, is normally the desired
behaviour.

Set an explicit list only in the less common cases where the default list is
unsuitable: when the trust anchor list is large enough that sending it in full
is a burden, or when advertising the full list would expose an unusual, client-
identifying configuration. In those cases supply a relevant subset, or an empty
list, to limit what is disclosed; see the privacy considerations of the draft.
