=head1 NAME

sym - OpenSSL exported symbol files

=head1 SYNOPSIS

 # Symbols exported by this library.

 X509_verify_cert
 EVP_PKEY_new
 BF_cbc_encrypt                  BF,DEPRECATEDIN_3_0
 EC_GF2m_simple_method           DEPRECATEDIN_3_0,EC,EC2M
 OPENSSL_fork_prepare            DEPRECATEDIN_3_0    platform=UNIX
 OCSP_crlID_new                  OCSP                platform=!VMS

=head1 DESCRIPTION

F<util/libcrypto.sym> and F<util/libssl.sym> record the symbols each
library exports, and the conditions under which each one exists.  There
is one file per library.

Each line describes one symbol.  A line is a symbol name, optionally
followed by a feature list, optionally followed by attributes:

 line       = symbol, [ spaces, features ], { spaces, attribute };
 spaces     = space, { space };
 space      = " " | "\t";
 symbol     = ( letter | "_" ), { letter | digit | "_" };
 features   = feature, { ",", feature };
 feature    = ( letter | "_" ), { letter | digit | "_" };
 attribute  = "platform=", platform | "type=", type;
 platform   = [ "!" ], ( letter | "_" ), { letter | digit | "_" };
 type       = "FUNCTION" | "VARIABLE";

A B<#> begins a comment, which runs to the end of the line.  Blank lines
are ignored.

=head2 Features

The feature list names the build features the symbol depends on.  All of
them have to hold for the symbol to exist, so the list is read as a
conjunction: C<BF,DEPRECATEDIN_3_0> means the symbol exists only when
Blowfish is enabled B<and> the symbols deprecated in 3.0 are present.
There is no way to spell a disjunction.

A feature name is the name of an B<OPENSSL_NO_> macro with that prefix
removed, so the feature C<BF> corresponds to B<OPENSSL_NO_BF>.

A symbol with no feature list exists in every configuration.

=head2 Attributes

=over 4

=item B<platform=>I<platform>

The symbol exists only on I<platform>, or, with a leading B<!>, on every
platform except that one.  The platform names are the ones the build
recognises, such as B<UNIX>, B<_WIN32> and B<VMS>.

A symbol whose exported spelling differs on one platform appears as two
entries with opposite platform attributes, one naming each spelling.

=item B<type=>I<type>

B<FUNCTION> for a function and B<VARIABLE> for an exported variable.

=back

Both attributes may be omitted.  A symbol with no B<platform> exists on
every platform, and a symbol with no B<type> is a B<FUNCTION>.

=head2 Order

The order of the lines carries no meaning.  Nothing reads the file in
order, no two lines interact, and no position in the file is more correct
than any other.  New symbols may be added anywhere.

The file is deliberately not sorted.  Sorting it would invite a
convention that it stays sorted, and that convention would put every new
symbol in a position determined by its name -- which is the arrangement
this format exists to avoid.  See L</Merging>.

=head2 Merging

Because the lines are unordered and independent, two branches that each
add symbols have nothing to resolve: the correct result is both sets of
lines.  F<.gitattributes> declares this, so git merges them without
conflict:

 util/*.sym                              merge=union

A union merge keeps every line from both sides.  It can therefore produce
a file with a symbol listed twice, if two branches added the same name or
one branch edited a line another branch also touched.  That is caught
when the file is read rather than by git, and the fix is to delete the
surplus line.

=head1 EXAMPLES

A symbol present in every configuration:

 X509_verify_cert

A symbol that exists only when a feature is enabled:

 TS_RESP_print_bio               TS

A symbol that requires two features at once:

 EC_GF2m_simple_method           DEPRECATEDIN_3_0,EC,EC2M

A symbol that exists only on one platform:

 RAND_screen                     DEPRECATEDIN_1_1_0  platform=_WIN32

A symbol exported under a different name on VMS, written as two entries:

 ERR_load_CRYPTO_strings         DEPRECATEDIN_3_0    platform=!VMS
 ERR_load_CRYPTOlib_strings      DEPRECATEDIN_3_0    platform=VMS
